## 每日 Codex 训练复盘

**使用场景:** 完成 30 天训练营中的一天后，用 10 分钟复盘今天是否真的掌握了一个 Codex 能力点。

**负责人:** 个人学习者

**cadence:** 每天训练结束后

**目标:** 把当天理论、实操、Prompt 和成果物沉淀成下一次可复用的经验。

**输入字段:**

### 项目 1

**字段键:** today_goal

**label:** 今日目标

**placeholder:** 例如：学会用 GCCD 写清楚 Codex 任务。

### 项目 2

**字段键:** artifact

**label:** 完成成果物

**placeholder:** 例如：一份可复制的项目结构说明 Prompt。

### 项目 3

**字段键:** stuck_point

**label:** 卡点

**placeholder:** 例如：不知道如何描述 Definition of Done。

### 项目 4

**字段键:** next_action

**label:** 明日行动

**placeholder:** 例如：用同一套 Prompt 让 Codex 检查一个真实仓库。


**复盘问题:**

- 我今天是否能用自己的话解释这个能力点？
- Codex 的输出里哪些信息需要人工验证？
- 今天的 Prompt 哪一句最关键，哪一句是噪音？
- 如果明天继续做，我会减少哪一个不必要步骤？

**outputSections:**

- 今日结论
- 有效做法
- 问题与原因
- 可复用 Prompt
- 明日行动

**codexPrompt:**

你是一名 Codex 学习教练。请根据我提供的今日目标、成果物、卡点和明日行动，帮我生成一份每日 Codex 训练复盘。要求：1. 判断我是否真的掌握了今天的能力点；2. 提炼一个可复用经验；3. 指出一个明天必须验证的问题；4. 输出中文，结构包括今日结论、有效做法、问题与原因、可复用 Prompt、明日行动。


**最佳实践:**

- 复盘时不要只写“学会了”，要写清楚可观察证据。
- 把卡点转化成下一次给 Codex 的任务，而不是停留在情绪描述。
- 每天只沉淀一个最重要 Prompt，不追求数量。

**标签:**

- 每日复盘
- 30天训练营
- 学习闭环
- Prompt

## Prompt 迭代复盘

**使用场景:** 一个 Prompt 经过多轮修改后，用复盘找出真正影响输出质量的变量。

**负责人:** Prompt 使用者

**cadence:** 每次关键 Prompt 迭代后

**目标:** 把一次 Prompt 调优过程变成可复用的写法规则。

**输入字段:**

### 项目 1

**字段键:** original_prompt

**label:** 原始 Prompt

**placeholder:** 粘贴第一版 Prompt，保留真实上下文。

### 项目 2

**字段键:** final_prompt

**label:** 最终 Prompt

**placeholder:** 粘贴效果最好的一版 Prompt。

### 项目 3

**字段键:** quality_gap

**label:** 质量差异

**placeholder:** 例如：最终版输出更结构化，但仍缺少验证步骤。

### 项目 4

**字段键:** reuse_rule

**label:** 复用规则

**placeholder:** 例如：先写业务场景，再写输入字段，最后写输出格式。


**复盘问题:**

- 哪一个新增上下文最明显改善了结果？
- 哪一个约束让输出更可执行？
- 最终 Prompt 是否包含验收标准？
- 这套写法能否迁移到另一个场景？

**outputSections:**

- 迭代前问题
- 关键改动
- 质量提升证据
- 复用规则
- 下一版优化

**codexPrompt:**

你是一名 Prompt 质量审查专家。请比较我提供的原始 Prompt 和最终 Prompt，分析质量提升来自哪些具体改动。要求：1. 不泛泛评价；2. 找出 3 个真正影响输出质量的变量；3. 提炼可复用写法规则；4. 指出下一版仍需要补充的信息；5. 输出中文复盘报告。


**最佳实践:**

- 不要同时改太多变量，否则很难判断哪一处有效。
- 保留失败版本，它比成功版本更能暴露上下文缺口。
- 每次 Prompt 复盘都要产出一条可迁移规则。

**标签:**

- Prompt
- 迭代
- 质量评估
- 复用规则

## 项目实战交付复盘

**使用场景:** 用 Codex 完成一个页面、工具或 Agent 原型后，复盘项目目标、实现路径、验证结果和下一步优化。

**负责人:** 项目负责人

**cadence:** 每次项目阶段交付后

**目标:** 把项目交付过程沉淀成下一次可复用的工程执行方法。

**输入字段:**

### 项目 1

**字段键:** project_goal

**label:** 项目目标

**placeholder:** 例如：完成一个可搜索、可复制 Prompt 的页面。

### 项目 2

**字段键:** implementation

**label:** 实现路径

**placeholder:** 例如：新增 JSON 数据、组件、页面路由和收藏交互。

### 项目 3

**字段键:** verification

**label:** 验证结果

**placeholder:** 例如：typecheck、lint、build 通过，本地页面返回 200。

### 项目 4

**字段键:** tradeoff

**label:** 取舍

**placeholder:** 例如：本轮不接数据库，先用本地 JSON 保持 Vercel 部署简单。


**复盘问题:**

- 本次交付是否解决了最初目标，而不是只完成代码？
- 哪些任务适合 Codex 执行，哪些必须人工判断？
- 验证是否覆盖了用户真正会访问的页面？
- 下一次可以提前写进 AGENTS.md 的规则是什么？

**outputSections:**

- 交付摘要
- 完成证据
- 工程取舍
- 风险残留
- 下一步任务

**codexPrompt:**

你是一名资深工程负责人。请根据我提供的项目目标、实现路径、验证结果和取舍，生成一份项目实战交付复盘。要求：1. 用交付结果说话；2. 明确哪些工作由 Codex 高效完成；3. 标注仍需人工判断的风险；4. 提炼下一次项目可复用的执行规则；5. 输出中文，适合放入项目状态文件。


**最佳实践:**

- 交付复盘必须包含验证命令或页面验证证据。
- 不要只列功能，要说明为什么这样设计。
- 把重复出现的经验沉淀到 AGENTS.md 或项目状态文件。

**标签:**

- 项目实战
- 交付
- 工程管理
- 验证

## Bug 修复复盘

**使用场景:** 修复构建失败、页面打不开、链接失效或交互异常后，沉淀排查路径。

**负责人:** 开发者

**cadence:** 每次重要问题修复后

**目标:** 把一次排障过程变成下次更快定位问题的检查清单。

**输入字段:**

### 项目 1

**字段键:** symptom

**label:** 现象

**placeholder:** 例如：Vercel 主域名显示 404: NOT_FOUND。

### 项目 2

**字段键:** root_cause

**label:** 根因

**placeholder:** 例如：Vercel 项目 Framework Preset 被识别为 Other。

### 项目 3

**字段键:** fix

**label:** 修复动作

**placeholder:** 例如：新增 vercel.json 固定 Next.js 构建配置。

### 项目 4

**字段键:** prevention

**label:** 预防措施

**placeholder:** 例如：部署前必须运行 build 并 inspect Vercel 状态。


**复盘问题:**

- 我最初的判断是否偏离根因？
- 哪个证据真正证明了问题来源？
- 修复动作是否有副作用？
- 如何把这次问题变成自动检查或文档规则？

**outputSections:**

- 问题现象
- 排查路径
- 根因判断
- 修复动作
- 预防清单

**codexPrompt:**

你是一名 Debug 复盘专家。请根据我提供的问题现象、根因、修复动作和预防措施，生成一份 Bug 修复复盘。要求：1. 按时间顺序还原排查路径；2. 区分猜测和证据；3. 说明修复动作为什么有效；4. 输出可复用预防清单；5. 中文输出，语气专业简洁。


**最佳实践:**

- 排障复盘要区分症状、根因和修复动作。
- 不要把偶然恢复当成根因修复。
- 能脚本化的检查应进入 npm script 或部署文档。

**标签:**

- Debug
- 故障复盘
- 构建
- 部署

## 安全售前拜访复盘

**使用场景:** 完成零信任、SASE、数据安全、XDR 或 MSS 客户沟通后，整理客户画像、需求信号和下一步动作。

**负责人:** 安全售前

**cadence:** 每次客户拜访后 24 小时内

**目标:** 把一次客户沟通转化为可跟进的方案线索和行动计划。

**输入字段:**

### 项目 1

**字段键:** customer_context

**label:** 客户背景

**placeholder:** 例如：金融行业，总部加分支，正在推进零信任改造。

### 项目 2

**字段键:** pain_points

**label:** 痛点信号

**placeholder:** 例如：远程办公访问慢、终端风险不可见、数据外发审计弱。

### 项目 3

**字段键:** stakeholders

**label:** 关键人

**placeholder:** 例如：安全负责人关注合规，网络负责人关注体验。

### 项目 4

**字段键:** next_step

**label:** 下一步

**placeholder:** 例如：准备一版分阶段零信任建设方案和 PoC 验证清单。


**复盘问题:**

- 客户真正的业务压力是什么？
- 哪些信息是明确事实，哪些只是推测？
- 方案下一步应该验证技术可行性还是争取业务共识？
- 我需要 Codex 帮我生成哪份材料？

**outputSections:**

- 客户画像
- 需求信号
- 关键人判断
- 方案机会
- 下一步行动

**codexPrompt:**

你是一名资深网络安全售前负责人。请根据我提供的客户背景、痛点信号、关键人和下一步，生成一份客户拜访复盘。要求：1. 明确事实与推测；2. 提炼客户核心业务压力；3. 给出可落地的方案机会；4. 输出下一步材料清单；5. 不编造未知信息，未知处标注待确认。


**最佳实践:**

- 安全售前复盘必须区分事实、判断和待确认信息。
- 不要一上来写产品功能，要先写客户业务压力。
- 下一步行动必须能落到材料、会议、PoC 或内部协同。

**标签:**

- 安全售前
- 客户画像
- 方案机会
- 复盘
