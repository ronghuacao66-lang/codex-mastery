## Day 1 · 认识 Codex 与项目体检

**天数:** 1

**建议用时:** 60-90 分钟

**学习目标:** 理解 Codex 的工程定位，并完成一次真实仓库体检。

**理论:** Codex 不是普通聊天工具，而是面向软件工程任务的 coding agent。第一天的重点不是让它写代码，而是训练你把 Codex 当成工程同事：先读仓库、识别技术栈、确认运行命令、发现风险，再决定下一步。

**核心概念:**

- Codex 适合仓库级任务：读代码、改文件、运行命令、验证结果。
- 第一次使用不要直接要求大改，先让 Codex 建立项目地图。
- 优秀用户会要求 Codex 区分事实、推断和待验证信息。

**实操任务:** 选择一个已有前端项目，让 Codex 完成项目体检。

**执行步骤:**

- 打开一个真实项目仓库，确认你能本地看到代码。
- 让 Codex 只读取文件，不修改文件，输出技术栈、目录结构、入口页面和运行命令。
- 要求 Codex 标出它无法确认的信息，例如缺少 README、缺少 env、缺少测试命令。
- 人工核对 package.json、README、app/pages/src 目录，判断 Codex 是否读对。
- 把体检结果整理成一份项目说明，作为后续任务上下文。

**起始输入:**

- 项目路径
- package.json
- README 或启动说明
- 你希望最终改造的页面或模块

**Prompt:** 请阅读当前仓库，但不要修改任何文件。输出：1. 项目技术栈；2. 目录结构和关键入口；3. 本地运行、类型检查、测试、构建命令；4. 主要页面或模块；5. 当前项目风险；6. 你无法确认但需要我补充的信息。请区分事实、推断和待验证项。

**成果物:** 一份项目体检报告，包含技术栈、目录地图、运行命令、风险和待补充信息。

**验收标准:**

- Codex 没有修改文件。
- 报告中的命令能在 package.json 或 README 中找到依据。
- 至少列出 3 个关键目录或入口文件。
- 至少列出 3 个待验证项或风险。

**常见错误:**

- 一开始就让 Codex 重构整个项目。
- 不要求它说明依据，导致报告像猜测。
- 没有人工核对运行命令。

**进阶任务:** 把体检报告压缩成 10 行项目上下文，以后每次给 Codex 下任务时复用。

**复盘问题:**

- 我是否能说清 Codex 与 ChatGPT 的区别？
- 体检报告中哪些是事实，哪些是推断？
- 下一次任务我需要补充哪些上下文？

**标签:**

- 入门
- 项目理解
- 仓库阅读
- 实战

## Day 2 · GCCD：写出可执行任务

**天数:** 2

**建议用时:** 60-90 分钟

**学习目标:** 掌握 Goal、Context、Constraint、Definition of Done，并用它改写一个真实需求。

**理论:** Codex 任务失败通常不是模型不会，而是任务没有边界。GCCD 把模糊愿望变成工程委托：Goal 定义结果，Context 给出项目事实，Constraint 限制范围，Definition of Done 定义完成标准。

**核心概念:**

- Goal 只能有一个主目标，不要把多个项目塞进一天。
- Context 需要包含技术栈、现有实现、用户场景和相关文件。
- Constraint 要写清不能做什么。
- DoD 必须能被构建、测试、页面检查或人工流程验证。

**实操任务:** 把“首页更高级一点”改写成 Codex 可执行任务，并让 Codex评审你的任务。

**执行步骤:**

- 写下一个模糊需求，例如“首页更专业”。
- 按 Goal / Context / Constraint / DoD 四段改写。
- 把改写后的任务交给 Codex，让它指出缺失信息和风险。
- 根据 Codex 的反馈补齐 2-3 条约束和验收标准。
- 保存最终版本到你的 Prompt 模板库。

**起始输入:**

- 模糊需求一句话
- 项目体检报告
- 目标用户
- 不可改动范围

**Prompt:**

请审查并改写我的 Codex 任务。原始需求：我想让首页更专业。请输出：1. 这个需求为什么不可执行；2. 改写后的 Goal；3. 必需 Context；4. Constraint；5. Definition of Done；6. 仍需我补充的问题。改写后的任务要能直接交给 Codex 执行。


**成果物:** 一条完整 GCCD 任务 Prompt，并附带 Codex 的任务质量反馈。

**验收标准:**

- 任务包含 Goal、Context、Constraint、DoD 四段。
- DoD 至少包含一个命令验证和一个页面体验验证。
- 约束中明确不改无关模块。
- Codex 能基于该任务给出明确实施计划。

**常见错误:**

- Goal 写成“优化一下”这种主观词。
- 只写要做什么，不写不能做什么。
- DoD 写成“看起来不错”。

**进阶任务:** 用同一方法改写一个 Bug 修复任务和一个工具开发任务。

**复盘问题:**

- 我的 DoD 是否可检查？
- 上下文是否足够让 Codex 不猜？
- 这个任务是否应该继续拆小？

**标签:**

- GCCD
- Prompt
- DoD
- 任务委托

## Day 3 · 先读代码，再给计划

**天数:** 3

**建议用时:** 75-100 分钟

**学习目标:** 训练 Codex 在修改前先建立代码上下文和实施计划。

**理论:** 专业使用 Codex 的关键动作是“先读后改”。你要让 Codex 找到相关文件、理解数据流和组件关系，再提出最小改动计划。这样可以显著减少无关重构和猜测式修改。

**核心概念:**

- 让 Codex 读取相关文件，而不是直接改。
- 计划必须包含文件范围、改动步骤、风险和验证。
- 用户要审查计划，再决定是否执行。

**实操任务:** 选择一个页面，让 Codex 先分析信息架构并给出最小改动计划。

**执行步骤:**

- 选一个具体页面，例如首页、列表页或详情页。
- 让 Codex 读取页面、组件、样式和数据文件。
- 要求它画出当前信息结构：数据从哪里来、组件如何渲染、状态在哪里。
- 要求它给出 3 个改进方向，并标明最小改动方案。
- 只选择一个低风险方案让 Codex 执行或暂存为计划。

**起始输入:**

- 页面路径
- 相关组件目录
- 数据文件路径
- 你观察到的问题

**Prompt:** 请先阅读这个页面及其相关组件和数据文件，暂时不要修改代码。输出：1. 当前页面信息架构；2. 数据流和状态来源；3. 相关文件清单；4. 3 个可改进点；5. 最小改动计划；6. 风险和验证方式。页面目标：让用户更快找到今天要做的任务。

**成果物:** 一份可执行改动计划，包含文件范围、步骤、风险和验证方式。

**验收标准:**

- 计划列出具体文件路径。
- 计划说明数据流或组件关系。
- 改动范围控制在一个页面或少数组件。
- 包含至少 3 条验证方式。

**常见错误:**

- 没有让 Codex 暂停修改。
- 计划只有抽象建议，没有文件和步骤。
- 用户不审计划就让 Codex 执行。

**进阶任务:** 把计划改写成一个新的 GCCD 任务，并放入任务生成器保存。

**复盘问题:**

- Codex 是否准确找到相关文件？
- 计划里有没有无关重构？
- 我能否判断这个计划的风险？

**标签:**

- 代码阅读
- 计划
- 前端
- 上下文

## Day 4 · 实现搜索：从需求到可验证交互

**天数:** 4

**建议用时:** 90-120 分钟

**学习目标:** 完成一个真实搜索功能，并学会定义搜索范围、空状态和验收方式。

**理论:** 搜索是最适合练习 Codex 的前端功能之一，因为它涉及数据模型、输入状态、过滤逻辑、空结果、移动端布局和验证。它能训练你把功能需求写成可测试行为。

**核心概念:**

- 搜索字段必须明确：标题、描述、标签、正文。
- 空状态是功能的一部分，不是可选装饰。
- 搜索要和分类、标签等筛选组合时保持一致。

**实操任务:** 给一个资源列表页实现搜索功能。

**执行步骤:**

- 选择一个列表页，例如 Prompt、项目或文章列表。
- 明确搜索范围：至少包含标题、描述和标签。
- 让 Codex 实现受控输入、过滤逻辑和空结果。
- 要求移动端下输入框宽度稳定。
- 手动测试 3 个关键词：命中多个、命中一个、无结果。

**起始输入:**

- 列表数据结构
- 需要搜索的字段
- 空结果文案
- 目标页面路径

**Prompt:** 请为当前资源列表实现搜索功能。搜索范围包括标题、描述、正文摘要和标签。要求：1. 搜索与现有分类或标签筛选组合生效；2. 空结果有清晰提示；3. 移动端无横向滚动；4. 不引入新状态库；5. 完成后说明手动验证步骤。

**成果物:** 一个可用搜索框、组合过滤逻辑和空结果状态。

**验收标准:**

- 输入关键词后列表实时更新。
- 空结果状态可见且文案明确。
- 搜索与分类/标签筛选组合正确。
- 375px 宽度下无横向滚动。

**常见错误:**

- 只搜索标题，用户找不到正文内容。
- 搜索后没有清空按钮。
- 过滤逻辑写在多个组件里导致状态不一致。

**进阶任务:** 加入搜索命中数量显示，例如“找到 6 条结果”。

**复盘问题:**

- 搜索字段是否符合用户真实检索方式？
- 空结果是否给用户下一步动作？
- 过滤逻辑是否集中且可维护？

**标签:**

- 搜索
- UI
- 验证
- React

## Day 5 · 复制按钮：把内容变成可行动资产

**天数:** 5

**建议用时:** 75-100 分钟

**学习目标:** 实现复制交互，并理解客户端组件、浏览器 API 和状态反馈。

**理论:** 学习平台最重要的交互之一是复制。Prompt、模板、工作流、笔记如果不能一键复制，就只是阅读内容。复制按钮训练你处理 client component、Clipboard API、成功反馈和复制格式。

**核心概念:**

- 复制内容要完整，不只是复制标题。
- 成功反馈要短而明确。
- 客户端组件范围越小越好。

**实操任务:** 为 Prompt 或模板卡片增加一键复制。

**执行步骤:**

- 选择一个卡片组件，确定要复制的完整文本。
- 封装 CopyButton，不把复制逻辑散落在每个页面。
- 使用 navigator.clipboard.writeText。
- 点击后显示“已复制”状态 1-2 秒。
- 验证复制到剪贴板后的格式是否可直接粘贴使用。

**起始输入:**

- 卡片组件路径
- 要复制的字段
- 复制后的 Markdown 格式
- 按钮放置位置

**Prompt:** 请为资源卡片实现可复用 CopyButton。要求：复制完整 Markdown 内容；点击后显示“已复制”状态 1.5 秒；按钮有图标和 aria-label；只在需要浏览器 API 的最小组件使用 use client；不要改动无关页面。

**成果物:** 可复用 CopyButton 组件，并在至少一个模块中接入。

**验收标准:**

- 点击后按钮状态变化。
- 剪贴板内容包含标题、场景和正文。
- 组件可在多个模块复用。
- 没有把整个页面强行改成客户端组件。

**常见错误:**

- 只复制 Prompt 正文，丢失使用场景。
- 复制按钮没有反馈。
- 把 clipboard 逻辑写进每张卡片。

**进阶任务:** 为复制内容增加标准 Markdown 标题和分段。

**复盘问题:**

- 复制结果是否可直接发给同事或粘贴给 Codex？
- 客户端组件范围是否足够小？
- 失败场景是否需要提示？

**标签:**

- 复制
- 客户端组件
- Clipboard
- 交互

## Day 6 · 收藏与本地学习状态

**天数:** 6

**建议用时:** 90-120 分钟

**学习目标:** 实现无需后端的收藏功能，并理解 localStorage 状态持久化。

**理论:** 收藏、已看、完成状态是学习平台的核心交互。localStorage 能让你在没有后端时完成个人化体验，但要注意首次加载、数据解析失败和状态命名。

**核心概念:**

- localStorage 适合轻量偏好，不适合敏感数据。
- 状态 key 要有命名空间，避免和其它项目冲突。
- 收藏逻辑要封装成 Hook。

**实操任务:** 实现收藏功能，并让刷新后状态仍然存在。

**执行步骤:**

- 定义 localStorage key，例如 codex-mastery:favorites。
- 封装 useFavorites，提供 favorites、isFavorite、toggleFavorite。
- 在资源卡片中接入星标按钮。
- 刷新页面验证收藏状态。
- 测试取消收藏和多个资源收藏。

**起始输入:**

- 资源 id 字段
- 收藏按钮位置
- localStorage key
- 需要接入的模块

**Prompt:**

请实现资源收藏功能。要求：1. 使用 localStorage 持久化；2. 封装 useFavorites hook；3. 收藏按钮使用图标、aria-label 和 active 状态；4. 支持取消收藏；5. 刷新页面后状态保留；6. 不接入后端。


**成果物:** useFavorites Hook、收藏按钮和至少一个模块的收藏接入。

**验收标准:**

- 刷新页面后收藏状态保持。
- 取消收藏后 localStorage 同步更新。
- 按钮有可访问标签。
- 异常 JSON 不会让页面崩溃。

**常见错误:**

- 把收藏状态只存在 React state。
- localStorage key 太泛，和其它项目冲突。
- 没有处理 JSON parse 失败。

**进阶任务:** 新增“只看收藏”筛选开关。

**复盘问题:**

- 哪些状态适合本地保存？
- Hook 是否能复用到视频和模板？
- 如果未来接后端，数据模型该如何迁移？

**标签:**

- 收藏
- localStorage
- Hook
- 状态

## Day 7 · 第一周复盘：建立 Codex 操作系统

**天数:** 7

**建议用时:** 90-120 分钟

**学习目标:** 复盘第一周所有 Prompt、交付物和错误，形成个人 Codex 操作清单。

**理论:** 第一周的目标不是完成很多功能，而是建立稳定工作法：先读代码、写 GCCD、限制范围、复制可行动内容、验证交付。复盘能把一次性经验变成下一周的系统能力。

**核心概念:**

- 每个 Prompt 都应该能被评分。
- 返工原因通常来自上下文不足或 DoD 不清。
- 个人模板库比临时发挥更可靠。

**实操任务:** 整理第一周所有任务，升级为 3 条个人常用模板。

**执行步骤:**

- 收集 Day1-Day6 使用过的 Prompt。
- 标记哪条 Prompt 结果最好，哪条导致返工。
- 让 Codex 按目标、上下文、约束、输出、验收五维评分。
- 把得分低的 Prompt 重写。
- 沉淀 3 条模板：读仓库、做小功能、修交互。

**起始输入:**

- 本周 Prompt 记录
- 本周交付物
- 失败或返工案例
- 项目体检报告

**Prompt:** 请审查我第一周使用的 Codex Prompt。按目标清晰度、上下文充分性、约束明确性、输出格式、验收标准五个维度评分。请指出返工风险，并把其中 3 条改写成可复用模板：读仓库模板、小功能实现模板、交互修复模板。

**成果物:** 第一周复盘报告和 3 条个人 Codex 模板。

**验收标准:**

- 至少复盘 5 条 Prompt。
- 每条 Prompt 有评分和问题。
- 产出 3 条可复制模板。
- 明确第二周要避免的 3 个错误。

**常见错误:**

- 不记录失败 Prompt。
- 模板没有 DoD。

**进阶任务:** 把 3 条模板放入网站 Prompt Center 或个人知识库。

**复盘问题:**

- 本周最大返工原因是什么？
- 我最常漏写的是 Context 还是 DoD？

## Day 8 · 数据模型先行：内容不是文案堆叠

**天数:** 8

**建议用时:** 90-120 分钟

**学习目标:** 为 Prompt Center 或项目中心设计可维护的数据模型。

**理论:** 内容型产品的质量不只取决于页面设计，更取决于数据模型。字段决定了搜索、筛选、复制、详情页和未来扩展能力。优秀的 Codex 用户会先定义类型和样例，再写 UI。

**核心概念:**

- 数据模型要服务用户动作，而不是只服务展示。
- 字段必须稳定、可搜索、可复制。
- 先写 3 条真实样例，比直接写 100 条更可靠。

**实操任务:** 设计一个 Prompt 资源的数据模型并生成真实样例。

**执行步骤:**

- 确定资源对象：Prompt、项目、文章或模板。
- 列出页面上需要展示和操作的字段。
- 写 TypeScript 类型。
- 写 3 条真实 JSON 样例。
- 让 Codex 检查字段是否支持搜索、筛选、复制和详情展示。

**起始输入:**

- 资源类型
- 目标用户
- 卡片展示字段
- 复制时需要的字段

**Prompt:**

请为一个中文 Codex Prompt Center 设计数据模型。要求：TypeScript 类型和 JSON 样例同时给出。每条 Prompt 包含标题、分类、难度、使用场景、Prompt 正文、输入要求、输出要求、最佳实践和标签。请先给 3 条真实可用样例，并说明这些字段如何支持搜索、筛选、复制和详情页。

## Day 28 · 质量审查：像 Reviewer 一样使用 Codex

**天数:** 28

**建议用时:** 120-150 分钟

**学习目标:** 让 Codex 对你的毕业项目做代码审查，并修复高优先级问题。

**理论:** Code Review 不是总结改了什么，而是找 Bug、风险、回归和缺失测试。让 Codex 进入 reviewer 角色，可以帮助你发现状态错误、类型风险、移动端问题和内容缺口。

**核心概念:**

- 审查要 findings first。
- 问题要有文件和行为影响。
- 只修 P0/P1，不做无关重构。

**实操任务:** 让 Codex 审查毕业项目，并修复最重要问题。

**执行步骤:**

- 让 Codex 读取最近改动或关键文件。
- 要求它按严重程度列 findings。
- 只选择 P0/P1 问题修复。
- 修复后运行验证。
- 记录残留风险。

**起始输入:**

- 毕业项目代码
- 测试或构建结果
- 关键用户路径
- 已知风险

**Prompt:**

请以代码审查姿态审查当前毕业项目。Findings first，按 P0/P1/P2 排序。重点关注 Bug、类型风险、移动端布局、状态逻辑、内容缺口、缺失验证。每个问题必须说明影响和建议修复。先不要做无关重构；只修复 P0/P1 问题，并运行验证。


**成果物:** 代码审查报告、高优先级修复和验证结果。

**验收标准:**

- 审查输出 findings first。
- 问题有具体影响。
- 只修复高优先级问题。
- 验证命令通过。

**常见错误:**

- 让 Codex 写总结而不是找问题。
- 一次修太多低优先级问题。
- 没有残留风险说明。

**进阶任务:** 把审查发现转成团队 PR 模板检查项。

**复盘问题:**

- Codex 找到了哪些我没发现的问题？
- 哪些问题应该写进 AGENTS.md？
- 还有哪些验证缺口？

**标签:**

- Code Review
- 质量
- 修复
- 回归
